# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Purpose

DataAnalyzer views and analyses time series recordings through a lightweight local HTTP server and a browser page. The two goals are (1) tweaking analysis parameters and seeing the result immediately, including filters still under development, and (2) watching intermediate results while an analysis script is running. The primary data is Open Ephys binary recordings from an Intan RHD headstage on a NeuroNexus A1x32-Poly2: 30 kHz, 32 headstage channels in µV plus 3 aux (accelerometer) channels. Two layouts exist and both must keep loading (see *Recording formats*): the older single-stream sessions (`ExampleSession/`, no longer in the repo) and the GLANCE sessions in `DATA/` with an online Ripple Detector. The main event of interest across all sessions is the sharp-wave ripple.

## Commands

```
python serve.py                              # starts with nothing loaded: choose the folder in the viewer
python serve.py --dialog                     # ...or open the native folder dialog first
python serve.py DATA                         # folder of sessions; switch session / stream in the viewer
python serve.py DATA/2026-09-18_09-15-01     # one recording (memory-mapped, never read whole)
python serve.py DATA --analyses filters_dev.py   # plus your reloadable analyses
python serve.py --demo                       # synthetic signal, no data needed
python serve.py --no-browser --port 8010

python detect_swr.py DATA --only "Record Node 110" --min-s 60   # ripple detection on every recording longer than a minute + online comparison table
                                             # --detector swr_nss (default, the standard offline method) | swr_laminar | swr
jupyter notebook notebooks/detection_methods.ipynb   # the same three methods written out from scratch, to check a run against
jupyter notebook notebooks/event_aligned.ipynb      # step by step: pick a recording and a TTL line, align on its rising/falling edge, trigger → stimulus latency
jupyter notebook notebooks/latency_comparison.ipynb # closed-loop latency (audio → trigger → stimulus) compared across sessions; add a session = one line in SESSIONS
python detect_spikes.py DATA/<session>       # threshold spike detection -> <recording>/dataanalyzer/[<stream>/]spikes/
                                             # (spike *sorting* with MountainSort5 is run from the viewer's Spikes tab)
python tests/test_dataanalyzer.py            # all tests (plain script, no pytest)
python tests/test_dataanalyzer.py server     # only tests whose name contains "server"
```

Only `numpy` is required; `scipy` is optional and every filter has a numpy fallback (`analysis.bandpass`, `envelope`, `welch_psd`). `spikeinterface` + `mountainsort5` are needed only for the Spikes tab's sorting (installed here; everything else runs without them). No build step, no package install: run from the repo root. Python 3.13, `uv` is available for environments. `tkinter` is not installed on this machine, so the folder dialog uses `osascript`.

## Architecture

Request flow: browser → `dataanalyzer/server.py` (stdlib `ThreadingHTTPServer`) → `analysis.REGISTRY[name].fn(window, channel, **params)` → min/max decimated JSON → canvas plot in `dataanalyzer/viewer/index.html`.

- **`io.py`** — `TimeSeries` holds `t` (seconds), `data` (n×k, may be a read-only int16 `np.memmap`), per-channel `scale`/`units`, and `events` (name → times) with optional `event_labels`. Channels have a **kind** (`ts.kinds()`: `headstage` | `aux` | `other`, from `channel_info[i]["kind"]`, else inferred from units); select electrodes with `ts.headstage_channels()` and the accelerometer with `ts.aux_channels()`, never by unit string (the Ripple Detector's `RIP_FEAT` is written in µV, GLANCE aux channels in `a.u.`). `ts.ttl` keeps each TTL line as on/off times (including the lines only a *sibling Record Node* of the same session recorded — see *Recording formats* — each tagged with its `node`), `ts.recording_meta` the processor parameters from settings.xml and every stream's channel names, `ts.format_notes` how time and inputs were read plus `warnings` (e.g. `duplicate_channels`), `ts.results_subdir` the stream folder for saved results. Always read samples through `ts.channel(name)` (float, physical units), `ts.block(lo, hi, names)` (several channels in one read) or `ts.window(t0, t1)` (shares memory); never touch `ts.data` directly, it may be unscaled integers. `ts.overview()` is a lazily built, cached per-bucket min/max of every channel (~20k buckets, one chunked pass over the file, 0.5 s for the example session) that makes the all-channel full-recording view cheap. `load()` dispatches on path: a directory or `structure.oebin` → `load_openephys` (finds the first `structure.oebin`, memmaps the chosen stream, builds the time axis with `_oe_time_axis`, puts the TTL events of *every* stream and processor on the loaded stream's clock via `sample_numbers.npy`, named `TTLn on/off` for the source's own lines and e.g. `Ripple Detector LFPStream-A TTL1 on` otherwise, plus MessageCenter text); `.csv/.tsv/.npy/.npz` otherwise.
- **`analysis.py`** — `multitaper_spectrogram(y, fs, win_s, step_s, nw)` averages the periodograms of 2·nw−1 Slepian (DPSS) tapers per window, which trades a little frequency smearing for far less variance; without scipy there are no DPSS sequences, so it falls back to a single Hann window and is an ordinary spectrogram. `band_power` integrates a spectrogram over a band. `@analysis(label, [Param(...)])` registers `fn(ts, channel, **params) -> Result` in `REGISTRY`. `Param` (float/int/bool/choice with min/max/step/help) is the schema the viewer turns into sliders and inputs, and `Analysis.coerce` clamps query-string values. `Result` is a list of `Trace`s sharing an x axis; `domain="frequency"` (e.g. `psd`) tells the viewer to zoom locally instead of refetching. `kind="events"` traces carry x only. `kind="image"` traces (`spectrogram`, `wavelet`) carry a frequency axis `f`, a 2-D `z` (n_f × n_x), `zlabel` and `log_f`; the server block-maxes columns to `IMAGE_MAX_COLS` and subsamples rows to `IMAGE_MAX_ROWS`, sends 1st/99th-percentile `zmin`/`zmax`, and the viewer draws them with a viridis scale (`drawImageTrace`), a frequency y-axis (log if `log_f`), a colour bar, hover readout, and one heat map per lane in the stacked view. Both analyses call `decimate_for` so a 30 kHz trace is reduced to ~4× `max_hz` before transforming; the wavelet is a Morlet computed as Gaussian filters in the frequency domain (`morlet_power`). An analysis declared with `multichannel=True` (e.g. `csd_map` in `csd.py`) uses every channel of the window and ignores the channel choice; a function with a `layout` keyword receives the probe layout from the server. Image traces may set `row_labels` (channel names on the y axis) and `cmap="diverging"` (symmetric range, block-mean rather than block-max when decimating). The viewer routes multichannel analyses to the single plot even when "All channels" is selected. `load_plugin(path)` executes a file so its decorators (re)register; re-registration by name overwrites.
- **`server.py`** — `DataServer.analyze` runs the analysis on the *visible window plus padding* (`WINDOW_PAD_S` / `WINDOW_PAD_FRAC`) so filter edges fall off-screen and parameter changes stay fast, then `result_to_json` slices to the exact window and decimates with `decimate_minmax` (never more than `points` samples per trace, peaks preserved, NaN gaps kept). Results are cached by (analysis, channel, params, window). `/api/multi` (`channels=all`, `unit:uV`, or a comma list) returns one lane per channel: raw comes from the overview when the window is coarser than the buckets, else from one `block` read; any other analysis runs per channel through the same cache and is refused above `MULTI_MAX_SAMPLES` per channel with a "zoom in" message. `LiveStore` holds traces pushed by running code, versioned so the viewer polls cheaply. `set_root(path)` scans for sessions (`list_sessions`, pruned at each `structure.oebin`; each entry carries `session` (the session folder) and `node` (`Record Node N`) so the viewer offers **one option per session** and puts its Record Nodes in the stream picker as `node 110 · BroadbandStream-A` — the nodes are one recording written with different processing — plus `duration_s` computed from the file size, which the viewer shows in the session list and filters with its "min length s" box, `?min_s=60`) and auto-opens the first; `open_session` refuses paths outside the root.
- **`swr.py`** / `detect_swr.py` — **`swr_nss` is the default ripple detector**: the standard offline method (Buzsáki lab; FMAToolbox `FindRipples`). The LFP is decimated to ~1250 Hz, band-passed 120–200 Hz (Butterworth, order 3), **squared**, smoothed with an 8.8 ms boxcar (11 samples at 1250 Hz — the one detail the published text leaves out, and without it the 2 SD edges jitter) and normalised to the mean and SD of that squared signal: the *normalised squared signal*. A ripple is an NSS peak over `high_sd` = 5; its start and end are the `low_sd` = 2 crossings either side; candidates closer than `merge_ms` = 30 ms are one event; 15–100 ms are kept and the rest are `rejected` with reason `duration`. One channel, no laminar criterion, no sharp wave; `channel="auto"` takes the contact whose ripple band carries the most power. Thresholds are SDs of a *squared* signal, which is far from normal, so "5 SD" is a convention of the method, not a probability (`nss_signal`, `nss_events`).
- **`swr.py`** (continued) — `swr_laminar`, this project's depth-aware SWR detector: all good electrodes decimated to ~1.5 kHz in chunks (`decimated`), per-channel ripple envelope as robust z over the whole session, *local* envelope = z minus the probe-wide median (cancels artefacts/EMG/CAR), ripple channel = centroid of the neighbour-supported depth profile (`channel="auto"`, `layer_confidence`, `layer_confident`), candidates on the pooled local z, sharp wave as a CAR-invariant deep-minus-shallow 2–40 Hz bipolar z (`sw_score`, optional `require_sw`), rejections `global` / `movement` / `no_sharp_wave`. A detector whose function takes `layout` gets the probe layout and may be run with channel `auto`; `Detector.thresholds` maps feature-trace names to the threshold lines the Events tab draws.
- **`dentate.py`** — `dentate_spikes`: peaks of the 1–200 Hz LFP (Butterworth, order 4) over **six times the median absolute amplitude** of that filtered signal, events at least `refractory_ms` = 50 ms apart (the largest of a close group wins). Each event spans where the signal is above half its peak. Dentate spikes are *positive* (`polarity`, switch it to find sharp waves instead), and `depth_profile` — the mean amplitude of the detected events on every electrode — is what says whether they really come from the dentate rather than being a sharp wave or an artefact; `channel="auto"` takes the contact whose own events are largest, the same rule the notebook uses.
- **`stim.py`** — `stim_artifacts`, stimulus times from the recording itself for procedures without a TTL pulse. Median across electrodes subtracted (on an unreferenced recording the mains transient is shared by every channel 120 times a second and would swamp it; a stimulus survives because its size differs per contact), |first difference| per channel in robust SDs (scales from stretches spread over the recording, saved as `stats["mad_<j>"]`), a hit = at least `min_channels` of the electrodes over `threshold_sd` at the same sample, hits within `merge_ms` = one event, kept when the median-across-electrodes score reaches `score_min`; episodes longer than `max_ms` are rejected as `duration` (movement, connector noise), `refractory_ms` and `train_gap_ms` (adds `train` / `pulse`) are optional. Events carry `channels_frac`, `amp_uV` (peak-to-peak as recorded, median across electrodes) and `max_channel`; channel `auto` = the electrode with the largest artefact. About 5 s per 6-minute session; the same events come out of the referenced and the raw branch. In the 2026-09-18 sessions the strong artefacts precede the recorded Ripple Detector pulses by ~35 ms, i.e. the online detector was firing on them.
- **TTL pulses, comparison, triggered averages** (`detect.online_detections`, `detect.compare`, `triggered.py`) — the pipeline is general purpose about what a TTL line means (a detector firing, a stimulus, a camera frame), so nothing names them after an event type. Every TTL line with pulses, from any source, is rebuilt on every load as an event set `pulses_<stream>_TTL<n>` labelled `TTL<n> pulses · <source>` (`online: True`, `kind: "pulses"`, never saved, not deletable): `start` = rising edge (= `peak`), `end` = the next falling edge, `pulse_width_ms`, the source processor's settings.xml parameters, and, when the stream recorded a processor's feature and threshold, `score` = `RIP_FEAT / RIP_ON` at the rising edge. The shown channel is `Ripple_Input` (1-based) when the source has one, else the first electrode. **Merging:** a stimulator that fires on both edges of a trigger records each stimulus as two pulses a fraction of a millisecond apart, so the Events tab has "merge pulses ms" (`detect.merge_pulses`, `POST /api/pulses`, saved per recording and stream in `dataanalyzer/…/pulses/pulses.json` because the sets are rebuilt from the files on every load, 0 = off): pulses whose gap (next rising edge minus previous falling edge) is at most that become one event from the first rising to the last falling edge, keeping `n_merged` and `merged_ms`, and the set reports `n_pulses` (as recorded) beside `n_events`. In `RecordingAfterTurn100526/2026-10-05_09-37-39` TTL2 holds 184 pulses 0.1 ms wide in pairs 0.067–0.1 ms apart; merging at 1 ms gives 92, one per trigger pulse on TTL1. `compare(a, b, tol_ms, causal=…)` matches b against a one-to-one, reports b events that fall on events a *rejected*, and the latency b.start − a.start summarised as mean, SD, median, range and the values themselves (the Compare box shows "mean ± SD" in its heading). With **causal** a b event only matches an a event that precedes it by at most `tol_ms`, which is what a trigger and the response it caused need — e.g. an SWR setup with one TTL line for the detection trigger and another marking the stimulus reaching the tissue: without it a pulse that happens to precede its trigger is matched too and the mean is meaningless (on 2026-09-23 data, −15.46 ± 38.47 ms loose vs 51.01 ± 26.42 ms causal) (`/api/compare`, the Events tab's *Compare detections* box; every event panel marks other sets' events with dashed lines). Event windows can be centred on `peak`, `start` or `end` (`align`, the Events tab's "align on"): a stimulus delivered at a pulse edge is studied by aligning on that edge. `triggered.triggered_average` (`/api/triggered`, the Events tab's fourth panel and "Triggered average" box) cuts one channel out around every event (default ±250 ms, as recorded or band-passed, each trial baseline-corrected on its pre-event part) and returns the mean, SD and up to `max_trials` single trials, drawn as overlaid raw traces under the average with the ±1 SD band and dotted lines at the median interval to neighbouring events. `norm` is applied to every trial before averaging so mean, SD band and trials share a unit: `none`, `baseline` (minus the trial's mean over the `base_ms` = 100 ms before the event), `baseline_z` (that, divided by the trial's SD over the same window) or `session_z` (the channel's mean and SD over the whole session, `triggered.session_stats`, from stretches spread across the recording and band-passed like the trials). In the Events tab, clicking a lane in the depth or CSD panel isolates that channel in the triggered-average panel (the lane is tinted / outlined); double-clicking it, or the panel's "⤢ enlarge" button, opens the large viewer (`#focus`, `drawTrigOn(id, big)`): ‹ › or arrow keys step through channels in depth order, the normalisation select mirrors the sidebar's, trials and ±1 SD can be toggled, the hover readout gives mean ± SD at the cursor, Esc closes. Canvases are absolutely positioned by a global CSS rule, so any new canvas needs a `position:relative` container.
- **`detect.py`** — whole-recording event detectors (`@detector`, same `Param` schema as analyses): `theta` (robust median/MAD z of theta power, computed at 1 kHz, saved with a whole-session `scan` for the Theta tab), **`theta_mt`** (the Theta tab's default: 5–12 Hz power from a **multitaper spectrogram**, 4 s window / 2 s step, `analysis.multitaper_spectrogram` + `band_power`, smoothed, and the bins above the **90th percentile of the whole session** — a percentile threshold always labels that share of the recording, so it asks "when was theta strongest *here*", not "was there theta"; the reference should be a contact where theta is large and steady, stratum oriens in the usual recipe, and `channel="auto"` takes the contact with the most theta power), `swr` and `immobility`. A detector returns `(events, stats)` or `(events, stats, extra)`; `stats` is the z-score reference, saved with the result so `features()` can recompute the identical detection signal on a short window later; `extra` is merged into the saved result. **SWR pipeline:** ripple-band envelope z on one channel → epochs → reject events the *reference channel* also shows (`ref_channel`, a `Param` of kind `"channel"`; `"auto"` is resolved by `DataServer.farthest_channel` to the contact farthest on the probe, else the far end of recorded order) → reject events during *movement* (`gate_movement`, robust-z of the accelerometer `motion_signal` built from every mV channel: high-passed, RMS across axes, smoothed). Rejected events stay in the result with `reason` = `reference` | `movement` and are browsable in the Events tab. `moving_average` is O(n) via cumsum (a direct convolve with a 1 s window at 30 kHz hung the server once) and `envelope` pads the Hilbert FFT to a fast length. Results are JSON in `<recording>/dataanalyzer/events/<name>.json`, or `<recording>/dataanalyzer/<stream>/events/` when the recording has several streams (for non-folder sources, `<stem>_dataanalyzer/events/`), loaded on session open; the server runs detections as background jobs (`start_job`, polled via `/api/jobs`).
- **`spikes.py`** / `detect_spikes.py` — chunked threshold spike detection (band-pass, MAD noise from the middle of the recording, negative peaks, per-channel refractory) saved to `<recording>/dataanalyzer/[<stream>/]spikes/spikes.npz` + `meta.json`. `backend="spikeinterface"` is wired but untested on these sessions. The viewer draws spikes as ticks per lane in Explore and can launch a run; `overview(result, duration)` (per-channel counts, rates, amplitude percentiles and a channel × time raster) and `waveforms(ts, result, channel)` (mean ± SD, single waveforms, amplitude and ISI histograms) are what the Spikes tab shows.
- **`phase.py`** — where in an ongoing rhythm each spike falls. The reference channel is decimated to ~1 kHz (`swr.decimated`), band-passed and turned into an analytic signal (`analytic`, an FFT Hilbert that does not need scipy); **0° = the peak of the band-passed signal, 180° = its trough**, in the recorded polarity. `event_ranges` turns an event set into the stretches to use (intersected with the Events tab's time ranges), `in_ranges` / `phase_at` assign each spike the phase of the nearest sample, and `phase_table` gives per group (a channel of the threshold detection, or a sorted unit) the phase histogram plus `circular_stats`: mean angle, mean vector length (0 = even over the cycle, 1 = all at one phase) and the Rayleigh test. `epoch_view` returns one epoch's reference LFP, its band-passed cycle and the spikes in it. Averaging whole epochs cancels the rhythm — they start at arbitrary points of the cycle — so `cycle_times` marks every cycle's peak (or trough) inside the epochs by interpolating the phase crossing, and `cycle_average` averages the reference channel on those, returning mean ± SD (each cycle on its own baseline), the band-passed mean and every group's spike rate on the same millisecond axis, ±¾ of a cycle by default. `rotate` sets what 0° means, and `cycle_times` reads `ph["align"]` so a rotated signal is not turned twice; the histograms and the average therefore always agree. `coherence_profile` measures theta **across the probe**: every electrode's phase-locking value and mean phase against one reference contact, over the epoch samples only, as a depth profile. Theta is coherent over the hippocampus but **reverses across the pyramidal layer**, so the largest phase step between neighbouring contacts that both follow the rhythm (`reversal`, contacts under `min_plv` ignored) is a layer landmark that needs no CSD and no ripples. `activity` is the session-long **theta / delta power ratio** (both bands from one decimated pass, reduced to ~3000 bins by their *mean* — an activity level is what the animal was doing over that stretch, not the largest thing in it), the usual proxy for how active the animal is, with the accelerometer (`detect.motion_signal`, robust z) interpolated onto the same bins when the recording has aux channels. Nothing is theta-specific — the epochs come from any event set and the band is a parameter — but the theta detector is the intended source, and it now saves a whole-session `scan` (`detect.scan_trace`, max-pooled robust z) and its `thresholds` with the result so the tab can draw the session without recomputing.
- **`sorting.py`** — spike *sorting* with **MountainSort5** through spikeinterface (both installed here; `available()` says so and the viewer reports it). Detection says when something crossed threshold on a channel, sorting says which cell each spike came from, by clustering the waveform shapes across neighbouring contacts. `sort_mountainsort(ts, layout=…)` wraps the open stream without copying — `si.BinaryRecordingExtractor` on the same `continuous.dat` with this project's names, gains and probe positions, then `si.ChannelSliceRecording` (spikeinterface 0.104 has no `Recording.channel_slice`), band-pass, optional whitening — runs scheme 1 (one pass) or scheme 2 (train on a stretch, then classify; `scheme="auto"` picks 2 above `SCHEME1_MAX_S` = 300 s), and keeps per unit the template on every channel, peak channel, µV peak-to-peak, SNR against that channel's MAD noise, firing rate and the share of ISIs below 1 ms. Channels flagged bad (`layout["bad"]`) are left out. Saved as `<recording>/dataanalyzer/[<stream>/]sorting/units.npz` + `meta.json`; `summary` (metrics + a unit × time raster) and `unit_detail` (template on the unit's strongest channels, ISI histogram) serve the viewer. A run is a background job — it is minutes on a long recording, and there is no way to cancel it short of restarting the server.
- **`probe.py`** — probe geometry (`Contact`/`Probe`), keyed by headstage input number so it joins `ts.channel_info`. Built-ins copied from `../Neuronexus/probe_map.py` (A1x32-Poly2, A4x8; H32 → RHD2132 routing); loaders for probeinterface JSON and CSV. `auto_probe` looks for `probe.json`/`probe.csv` near the recording, else assumes the Poly2 for 32 headstage channels (flagged ASSUMED). Only µV channels are placed on the probe. The viewer's Probe panel draws contacts coloured by recorded order, hover/click linking to lanes; verified that the example session's Channel Map is exactly the Poly2 depth order, tip first.
- **`csd.py`** — `depth_axis` (shallow → deep on the detection channel's shank), `csd` (second spatial derivative, Vaknin edges, optional 3-point Hamming across channels, sinks negative, µV/mm²), `event_view`, which builds the Events tab payload: LFP by depth, CSD, and detection features for one event or the peak-aligned average of all (`index=avg`), `csd_map` (the continuous Browse-tab map) and `layer_estimate`. **Layers:** after `../Neuronexus/openephys/oe/csd.py::identify_layers` — pyramidale = channel with the strongest ripple-band CSD *source* within ±`win_ms` of the event peak, radiatum / oriens = strongest baseline-subtracted wideband CSD *sinks* deeper / shallower than it — but the ripple-band source is measured per event and then averaged (ripples are not phase-locked, so an averaged LFP cancels them). Extents are the contiguous channels above half the peak. Saved to `<recording>/dataanalyzer/layers/layers.json`, loaded on session open, served by `/api/layers`; the viewer overlays them (`drawLayerOverlay`) on the CSD map, stacked lanes, both Events-tab depth panels and the probe panel (with the strength profiles as bars). `pyr_margin` < 1.5 or disagreement with the ripple-power peak means the profile is flat and the labels are not to be trusted; the sidebar flags both.
- **`channels.py`** — channel quality. `channel_quality` samples a few 30 s stretches and, per headstage contact, measures high-frequency noise (>300 Hz MAD), 1–300 Hz amplitude and the *best* correlation with its probe neighbours. Flags are relative to neighbours (log deviation from the two contacts either side, robust-z > 2.5 **and** at least a 1.5× difference) or a correlation drop, so the laminar amplitude gradient is not flagged but a single odd contact is. Manual `bad`/`good` overrides are merged by `effective_bad`; saved in `<recording>/dataanalyzer/channels/channels.json`. `interpolate_bad` replaces flagged rows by the linear interpolation of the nearest good rows and is applied before every CSD (event view, CSD map, layer estimate, event features). The server puts the bad list into `probe_layout()["bad"]`, which is how `depth_axis` learns it.
- **`features.py`** — per-event features written into the detection's JSON (`event["features"]`): duration, envelope z, peak frequency (zero crossings of the ripple-band signal inside the event), cycles, `burst_hz` / `burst_frac` (`excess_spectrum`: where and how much the ±50 ms around the peak adds to the spectrum over the 100 ms either side, mains harmonics excluded — the event's own frequency, whatever steady hum or rhythm surrounds it), ripple-band power and its ratio to 300–500 Hz, radiatum sharp-wave CSD sink and LFP deflection (the layer estimate's radiatum channel, else the strongest sink), spike-rate z (Poisson, from saved spikes), movement z and reference z. When the detection has `line_hz` (the laminar detector), mains harmonics are notched out of the ripple and control bands before measuring: without it a steady 180 Hz line sets the zero-crossing frequency of every event (synthetic 150 Hz ripples read 180 Hz). `table`/`to_csv` serve `/api/features`; `apply_filter` moves failing accepted events to `rejected` with reason `filter:<feature>` and `restore_filtered` undoes it. The Events tab shows the table (sortable, CSV link) and min/max filters that mark rows live before "Reject failing" saves them.
- **`dialog.py`** — the folder dialog is opt-in (`serve.py --dialog`): with no PATH the server starts with nothing loaded and the viewer asks for a folder (**Choose folder…**, or paste a path beside it, `POST /api/root`), which also avoids a stale default pointing at a folder that has moved. `pick_folder()` is the native directory dialog (osascript → tkinter → zenity) and the remembered last folder in `~/.config/dataanalyzer/last_root`, used as the dialog's starting location.
- **`live.py`** — `publish(name, x, y, url=...)` for a *separate* process; in-process scripts use `serve_in_background(ts).store.publish(...)` instead.
- **`viewer/index.html`** — single file, no external requests or libraries (hand-rolled canvas plot, pan/zoom/hover, y-lock). The default view is a fixed-length window (`DEFAULT_WINDOW_S` = 10 s) that you scroll through with the strip under the plot, ◀ ▶ buttons, arrow keys (shift = whole window, Home/End), trackpad sideways or shift+wheel; the "length" input changes how much is shown at once, plain wheel zooms, and Full shows the whole recording. Choosing "All channels" or "All uV channels" switches to `drawStacked`: one lane per channel, each centred on its median, with one shared scale per unit (median peak-to-peak across lanes) and a log2 gain slider; lock y freezes that scale while you pan. Colours come from CSS custom properties on `:root` with a `[data-theme=dark]` override; the header's Light / Auto / Dark toggle (remembered in localStorage, overridable with `?theme=dark`) sets that attribute and `readTheme()` re-reads the palette before every canvas draw, so never hardcode a colour in the drawing code. Every parameter change is debounced and refetched; the plot redraws the old data at the new x-range immediately for smooth panning. The current analysis, channel, window and parameters are mirrored into the URL query string, so a view can be reloaded, bookmarked, or opened headless (e.g. `/?analysis=filtered&channel=CH5&t0=200&t1=201&low_hz=1&high_hz=300`).

The viewer has five tabs, one per goal (`setTab`: `browse` = Explore, `swr`, `events`, `spikes`, `theta`; `?tab=explore|swr|events|spikes|theta`):

- **Explore** — look at the loaded data: raw waveforms and basic analyses, recorded TTL events, spikes, live traces, and every event set as an overlay. No detection forms.
- **SWR** — detect sharp-wave ripples, the main target of the data. The form offers the detectors with `category == "swr"` (**`swr_nss` by default**, channel *auto*), band presets (120–200 = the standard method's band, 120–250, 150–250, 120–170 below the 180 Hz line), all parameters, and "save as" (`tag`): a tagged run is saved as `<detector>__<tag>` beside the default one (`detect.result_name`, `detect.detector_of`), so band or parameter variants can be compared. "Run on all recordings…" (`POST /api/swr/batch`, `DataServer.run_swr_batch`) runs the same settings on every recording under the folder (path filter, minimum length), broadband stream, channel chosen per recording. SWR runs compute event features right away. A run is shown as a whole-session scan (`/api/swr/scan`; the detector stores `scan`: local and probe-wide ripple z, max-pooled to ~6000 bins, `swr.scan_trace`) with thresholds, kept and rejected events (click one to open it in Explore), the depth profile the ripple channel came from (supported and raw, pooled contacts, sharp-wave sides, contacts left out), and a histogram of `burst_hz`. The all-recordings table (`/api/swr/sessions`, read from result files, nothing opened) lists every SWR run per recording; clicking a row opens it. Channel check and the CSD layer estimate live here.
- **Events** — event sets (the top panel can show **one channel** instead of the depth map: "show → single channel", channel picker next to it, defaulting to the channel the set was detected on; the CSD panel is hidden then. This is separate from clicking a lane, which only picks the triggered average's channel). Event sets: TTL pulses, the other detectors (run from its "Detect events" box: stimulation artefacts, theta, immobility), and only those SWR runs **imported** from the SWR tab (`setImported`, remembered per recording and stream in localStorage; `eventSets()` is what the Events tab and Compare list). The **Time range** box restricts the tab to *included* stretches of the recording (`sections.py`, saved as `dataanalyzer/…/sections/sections.json` `{"include": [[t0, t1], …]}`, none = whole recording; `/api/sections`): an event counts only when it lies entirely inside one (`sections.event_in`). Stretches can be taken out as well as put in — the "drag" select switches what dragging on the strip does, and the typed boxes have **Include** and **Exclude** — `POST {"exclude": [...]}` subtracts them from what is included, starting from the whole recording when nothing is (`sections.subtract`). `DataServer.restrict` applies that to the average of all events, the triggered average and Compare (restricted events carry `_i`, their index in the full set, so compare rows still point at the right event); `events_json` sends `excluded` / `rejected_excluded` indices so stepping skips them, and the feature table and CSV mark `in_range`. Single events outside can still be opened (flagged). The strip draws the median peak-to-peak across electrodes over the session from the cached overview (`sections.activity`, log scale) with the chosen set's events; drag on it to add a range. **Suggest** (`sections.suggest`) proposes ranges leaving out flat (< 0.2 × session median: unplugged) or very large (> 8 ×: loose connector) stretches of at least 0.5 s — shorter blips such as stimulation artefacts are events, not bad recording. The Events panels are sized by what they hold rather than squeezed into one screen: the depth and CSD panels grow with the channel count ("lane px", default 16, remembered — 32 lanes give a 572 px depth panel), the recorded-features and triggered-average panels are fixed, and `#evmain` scrolls. A panel shows the **recorded detection features**: the channels a processor wrote beside the electrodes (`RIP_FEAT` with its thresholds `RIP_ON` / `RIP_OFF`), cut out around the event like the traces, averaged with them in the average view, thresholds dashed and the last value of each in the caption. `io.find_extra_channels` looks in the open stream, then the recording's other streams, then the other Record Nodes of the session, and only considers a stream that holds *electrodes* as well (a stream of its own, such as the GLANCE IMU stream, is not a processor's feature) and that actually recorded samples; loading it is wrapped so the panel can never fail an event view, and `DataServer.extras_source` loads that stream once and keeps it: in the 2026-09-23 recordings only the *LFP* stream of the node downstream of the detector carries them (35 ch = 32 + RIP_*), so a broadband view fetches them from there and the panel title names the stream. Note that only the stream whose channels are recorded has its feature stored: the broadband detector's own `RIP_FEAT` is not in those files, so a broadband detection (TTL3) is shown beside the *LFP* detector's feature. The Events tab has no detector-computed features panel any more; the viewer asks `/api/event` with `features=0`, which skips computing those traces (they cost ~120 ms per event for `swr_laminar`).
- **Spikes** — single-unit activity in the open stream, in two modes (the "show" select): **detected spikes** (threshold crossings from `spikes.py`: a channel list with counts and rates, a channel × time raster, and one channel's waveforms with its amplitude and ISI histograms, `/api/spikes/overview`, `/api/spikes/channel`) and **sorted units** (MountainSort5: a unit list with rate, SNR and refractory violations, a unit × time raster, the selected unit's template on the channels that carry it, and its ISI histogram with the 1 ms line, `/api/units`, `/api/unit`). Both runs are launched from this tab's side panel (`POST /api/spikes`, `POST /api/sort`) and are background jobs.

- **Theta** — high-theta epochs and the phase of the cycle the spikes fall on. "Align on" (peak or trough) sets both what counts as 0° and what the cycle average is aligned to. "Detect high-theta epochs…" runs either theta detector — a **method** select, `theta_mt` (multitaper, percentile) by default, falling back to `theta` (robust z); the form shows the parameters of whichever is chosen; "epochs from" then picks *any* event set as the stretches to use, so the same panels answer the question for a stimulation or an SWR set. The phase reference (channel, band) and the spike source (detected spikes or sorted units) are chosen beside it. Seven panels: the whole-session theta z with its thresholds and the epochs shaded (click one), the **theta / delta ratio** over the session with the accelerometer beside it (`/api/theta/activity`, delta band and smoothing in the sidebar) — high while the animal runs or explores, low while it sits still, grooms or sleeps, which is when ripples happen — the selected epoch with the reference channel, its band-passed cycle (drawn at its own scale — the band is a few µV inside a much larger signal) and a spike raster per group, the **average cycle** (the reference channel averaged on every cycle peak or trough inside the epochs, mean ± 1 SD with the band-passed mean and the selected group's spike rate behind it, `/api/phase/cycle`), the **phase by depth** profile (every contact's phase against the reference with its phase-locking value beside it, the reversal dashed and named — `/api/theta/coherence`, "min PLV" in the sidebar; its grid row is sized by the channel count, because a panel whose canvas is absolutely positioned does not grow a `grid-auto-rows` row), the selected group's phase histogram over two cycles with its mean phase, and every group's phase bins relative to an even spread, marked where the Rayleigh test says p < 0.05. Arrow keys step epochs; the group list sorts by locking strength, count, phase or recorded order. `/api/phase`, `/api/phase/epoch`, `/api/phase/cycle`, `/api/theta/coherence`, `/api/theta/activity`. The spike panels need a saved spike or sorting result; without one `spike_source` raises `FileNotFoundError`, which the GET handler turns into a 400 with the message (it is not a `ValueError`, so it used to kill the connection and the viewer showed only "Failed to fetch"). `DataServer._phase_inputs` catches it and carries on with an empty spike source, so the epochs, the session scan, the activity trace, the selected epoch, the average cycle and the phase-by-depth profile all work on a recording with no spikes; only the group list and the phase histograms say so (`spikes_note`).


Explore (the scrolling multi-lane view, with detections drawn as shaded spans, ‹ › buttons on every detection *and* every recorded event (TTL lines, messages) that centre the window on the previous / next one, `[` `]` (or `p` `n`) to step through everything that is ticked, merged in time (`jumpTo` / `jumpShown`; the "3/6 at …" note stays in the status line through the refetch), and the Detect spikes form) and Events (event list, LFP-by-depth lanes, CSD heat map, and the detector's feature traces with its thresholds; arrow keys step events; "Explore ↗" jumps to the event in the Explore tab). Stacked lanes can be coloured like the Open Ephys LFP viewer ("colours" under the gain slider: single, repeating palette or gradient along the recording, in groups of 1–16 channels; `laneColor(name)` keys the colour to the channel's recorded position, so it survives reordering and subsets, and the probe panel uses the same colours; `?colors=palette&group=4`). The divider between the side panel and the plot is draggable (`.resizer`, `setSideWidth`; one `--side-w` shared by the Browse and Events panels, remembered, double-click resets), and event / detection labels wrap rather than truncate. The Events tab's top panel shows the *unfiltered* samples by depth (`event_view` returns them as `raw`, reduced with `_decimate_rows_minmax` so spikes survive); "overlay band-passed LFP on the raw traces" draws the band-passed `lfp` over them in a third colour, on the **same µV scale**, so it reads as the part of the raw trace it is — with an "overlay ×" magnifier (1 / 2 / 5 / 10 / 20, remembered) because a ripple band is tens of µV inside a signal of hundreds, and the caption names the band and the factor. The band-passed trace is only shown on its own when the view has no `raw`. The single-channel view follows the same rule. The CSD and its overlay always use the band-passed `lfp`. In the Events tab the CSD heat map carries each channel's LFP waveform on its row ("overlay LFP waveforms on the CSD", on by default, same gain slider as the LFP panel, drawn in `--csd-ink` because the map is light in both themes); the Browse-tab CSD map has the equivalent `show_lfp` parameter. The **Chain** button toggles a strip under the header that draws the recording's signal chain from settings.xml (`io.oe_signal_chain`, served as `meta.data.signal_chain`): source → processors on this stream's Splitter branch → the Record Node that wrote the open files, with processors that alter the data outlined, channel-count changes (the Ripple Detector's 35 → 38), warnings (a Ripple Detector with no band-pass upstream), other branches dashed, and every settings.xml parameter on click. `?tab=events`, `?det=swr,theta`, `?cmp_a=swr_laminar&cmp_b=pulses_…` and `?probe=1` set these from the URL. The channel dropdown offers `kind:headstage` ("All headstage channels") next to `all` and `unit:<u>`.

`notebooks/detection_methods.ipynb` writes the three published methods out again from scratch — plain numpy and scipy, importing nothing from `dataanalyzer` but the loader — runs them on a recording, and compares each against the result the viewer saved, event by event. It is the check that the app's implementation is the method it claims to be: on `Oct062026_StimTestAndRecord/2026-10-06_15-29-14` the two agree on 278/278 ripples and 19/19 dentate spikes within 25 ms and on 18 high-theta epochs / 62 s. When they disagree the usual causes are a different `auto` channel (each method picks its own, and both print it), the Events tab's time ranges, or events within a second of either end.

HTTP endpoints are listed in the `server.py` module docstring. The viewer is the only client, so endpoint changes need matching edits there.

## Adding an analysis

Write a function in `filters_dev.py` (or another file passed with `--analyses`) using `@analysis` and `Param`; press Reload in the viewer. Keep it a pure function of the window it is given: z-scores, thresholds and PSDs are computed over the visible window by design, which is what makes them fast, so document that in the docstring (it is shown in the viewer). Built-in analyses live in `analysis.py` and serve as templates.

There is no Node or Playwright here. Headless Chrome works: start the server with `--no-browser --port 8765`, then run `/Applications/Google Chrome.app/Contents/MacOS/Google Chrome --headless=new --disable-gpu --user-data-dir=/tmp/da_chrome --window-size=1400,900 --virtual-time-budget=15000 --enable-logging=stderr --screenshot=/tmp/shot.png "http://127.0.0.1:8765/?analysis=filtered&channel=all&theme=dark"` in the background, wait for the PNG, then `pkill -f user-data-dir=/tmp/da_chrome`. ## Recording formats

`DATA/` is organised as `<animal-or-day>-<what>-<date>/<Open Ephys session>/Record Node N/…` (`D1-Opto-0914` = opto stimulation, older single-stream format, Record Node 104, 43 channels incl. 8 floating ADC inputs, 1-sample TTL2 pulses from the Ripple Detector marking the stimulation; `D4-Stim-0918` = the six GLANCE sessions). A session is usually written by **several Record Nodes** (one per Splitter branch), and a processor's TTL output is only saved by the node downstream of it: in the 2026-09-23 recordings the Ripple Detector sits on branch B, so its pulses exist only under `Record Node 121`, while `Record Node 110` has none of its own. All nodes share the acquisition clock, so `io._oe_sibling_events` adds the lines a sibling recorded to whichever node is open, named `… (Record Node 121)`, skipping a line both nodes recorded (`_same_line`: same source, line and edges within 2 ms). `load_openephys` handles both formats by inspection (no format switch); `tests/test_dataanalyzer.py` builds a fake of each (`make_fake_openephys`, `make_fake_glance`) and both must keep passing.

| | older sessions (`ExampleSession`) | GLANCE sessions (`DATA/`, 2026-09-18 on) |
|---|---|---|
| streams | one | two Record Nodes × (30 kHz Broadband + 3 kHz LFP): node 110 = after Notch, Common Avg Ref, Channel Map, Ripple Detector (`-A`); node 121 = raw (`-B`) |
| headstage names | blank → named `CH<input>` from the Channel Map in settings.xml | `A_CH20`, `LFP_A_CH1`: the name is the witness for the input; the settings.xml map is *not* applied (its streams are unnamed and would match by channel count) |
| aux | `A1_AUX1..3`, mV | `A_AUX0_1..3`, `a.u.`, bit_volts 1.0 (raw ADC counts; movement is z-scored, so the unit does not matter) |
| extra channels | – | `RIP_FEAT`, `RIP_ON`, `RIP_OFF` (kind `other`); the 2026-10-01 recordings have none, and add a third stream `IMUStream-A/-B` (100 Hz, 10 ch: quaternion, acceleration, gyroscope) whose `continuous.dat` is **empty** when the IMU is not streaming — `load_openephys` refuses such a stream with a clear message and `list_sessions` leaves it out of the stream picker |
| `timestamps.npy` | valid (seconds, or ticks) | restarts every buffer → time = `sample_numbers.npy / fs`; same for events |
| saved results | `<rec>/dataanalyzer/<kind>/` | `<rec>/dataanalyzer/<stream>/<kind>/` |

Findings in the 2026-09-18 `DATA/` sessions worth remembering: only Broadband-A is depth ordered (LFP-A keeps headstage order); the **3 kHz LFP stream holds 16 distinct signals** (inputs (1,2), (3,4)… are bit-identical, in the raw node too; the loader warns), so use the broadband stream; CAR really was applied to the 32 electrodes on path A although settings.xml lists `affected=33,34,35`; raw path B carries 1–3.5 mV of 60 Hz common mode and clips; the online Ripple Detector had **no band-pass filter upstream**, so `RIP_FEAT` is the wideband RMS of its input (r = 0.98, `Ripple_Input` 30 → `A_CH3`) and its detections are amplitude artefacts that match no offline ripple; and **180 Hz (third mains harmonic) carries 91–99 % of the 120–250 Hz power** on path A, up to 177 µV rms, strongest on the tip contacts and different on every contact (the 60 Hz notch and the CAR do not touch it). `swr_laminar` therefore notches mains harmonics inside the ripple band (`line_hz`, `analysis.remove_line`) and rejects events whose *excess* spectrum over the flanking baseline is line-locked (`line_frac` > `line_max`, reason `line_noise`). An earlier note here said the surviving events cluster at 177–185 Hz; that was the peak-frequency feature measured *without* the notch. Measured properly (2026-09-22, 63 kept events, 4 sessions > 1 min) they spread over 104–190 Hz (`burst_hz`, median 160), but they add little over their surroundings (`burst_frac` median 0.1–0.4; only 7 of 63 add half their band power at 130–200 Hz), no session has a clear ripple layer, and the automatic channel keeps landing on the tip. Channel quality explains part of that: the tip contacts `A_CH20` (2–3× median high-frequency noise) and `A_CH13` (LFP flat vs neighbours) are flagged in every long session, and **headstage inputs 15–19, five consecutive Intan inputs, are uncorrelated with their probe neighbours in all four sessions** (a connector / adapter fault signature, not tissue). Treat these SWR counts as unvalidated.

## Analysis notes

- CSD treats the Poly2's two staggered columns as one 25 µm linear array (as the sibling project does); the 43 µm column offset is a working value. Conductivity is not applied, so CSD values are relative (µV/mm²).
- `swr_laminar` is the SWR detector to use; the single-channel `swr` (reference-channel and movement gate, no sharp-wave criterion) remains as a simple first pass. Thresholds are robust SDs of an envelope, which is skewed: plain noise crosses z = 5 for 20 ms about 0.3 times a minute, so every session yields a few events. Trust `layer_confident`, `sw_score` and the Events tab (including the rejected set), not the count. The Intan aux accelerometer is ~340 mV/g; the movement signal is z-scored robustly so rest sits at 0 and `move_z` ≈ 2 is a sensible default. Stats saved with a result (`centre`, `scale`, `robust`) are what the feature traces use, so re-running a detector after editing it keeps the browser consistent.
- Laminar landmarks measured on 2026-08-10 are recorded in `../Neuronexus/probe_map.py` (`LAYERS`): pyramidale ≈ 225–275 µm above the tip, sharp-wave sink ≈ 175 µm, oriens ≈ 325 µm.

## Gotchas

- Open Ephys channel names are blank for headstage channels. The Record Node sits downstream of a Channel Map processor, so `continuous.dat` is in *mapped* order (for this probe that is depth order). `_oe_channel_map` reads the map from `settings.xml` (searched upward from the recording folder) and names each recorded position by its headstage input, 1-based: recorded position 1 of the example session is `CH20`. Never reorder channels; the recorded order is what the user wants to see. `ts.channel_info` keeps `{recorded, input}` per channel and the viewer shows "rec #n" in the dropdown. Without a map the names fall back to recorded position. Aux channels keep their names (`A1_AUX1..3`) and are in mV, not µV.
- Open Ephys writes a channel-mask parameter (`channels`, `affected`, `reference`) as the channels that are *excluded*: `affected="33,34,35"` on a 35-channel stream means the common average ran on channels 1–32, and an empty value means all (checked against the data of both streams). `io._mask_text` turns it into the selected set for the chain strip. settings.xml is flat: a Splitter's first branch follows it and `<SWITCH number="n"/>` starts branch n.
- Acquisition can drop samples: continuous `sample_numbers.npy` then jumps (`SalineLatencyTest/2026-10-09_12-47-39` lost 117 ms in 3 places), so the time axis has gaps and sample index ≠ sample number − first. `_oe_events` looks each event's sample number up in the stream's own sample numbers; treating it as an offset put every event after a gap late by the samples dropped so far. A window cut with `ts.block` across a gap is squeezed in time.
- Ripple Detector `ripple_input` on the GLANCE broadband stream appears to count across streams: 1–35 are the broadband channels and 36+ the LFP stream's (40 = `LFP_A_CH5`), inferred from the saline latency tests (`SalineLatencyTest1014`), where 36/38/40 gave the LFP-path timing (audio → trigger 1–5 ms, triggers only at some phases of the stimulator's 10 ms grid) and 5 the broadband timing (0.3–0.9 ms). In those tests the stimulator (TTL2, pairs of 0.1 ms pulses) fires on the next tick of an exact 10 ms grid that drifts a few ppm against the recording clock whenever the Open Ephys audio device is Windows Audio (buffer 480, 192 or 144 samples alike) and, loosely (±1 ms), with DirectSound at 480 samples; only DirectSound with a 64-sample buffer removes it (`SalineLatencyTest1015`: detection → trigger 1.3 ± 0.7 ms vs ~5.4 ± 2.8 ms in the other three device × buffer sessions, detection itself 0.15 ms in all four), so the wait is set by the GUI's audio callback, not the stimulator. (The notebooks now call TTL6 the *digital input*, the Ripple Detector's TTL8 the *OpenEphys detection time* and TTL2 the *trigger*); the recorded LFP pulse does not mark when the detector received it (triggers come before the recorded LFP rise), so time the loop with the TTL lines.
- The GLANCE LFP stream's `timestamps.npy` holds 30 kHz acquisition ticks **per buffer** (every sample of a buffer carries the first sample's tick plus a negligible fraction), and its `sample_numbers.npy` may start from an unrelated count (`SalineLatencyTest1014/Minimum`: 267 s off the broadband clock; `Linear`: 1.3 ms). `_oe_time_axis` then uses `sample_numbers / fs` shifted onto the ticks at the buffer starts (exact in both sessions, residual 0), and events of another stream are placed through that stream's own time axis (`clocks` in `_oe_events`), not `sample_numbers / fs`.
- `timestamps.npy` starts at the acquisition clock offset (e.g. 90.23 s), not 0. The viewer shows those absolute times.
- The IMU sibling project documents a GLANCE writer that stores 30 kHz tick counts in `timestamps.npy`; `_oe_time_axis` detects and converts that case.
- Reading a full channel from the 1 GB memmap the first time costs ~1.4 s (strided disk read); the OS cache makes later reads fast. Windowed requests are milliseconds.
- `dialog._osascript` starts its script with `activate` (from a terminal the macOS dialog otherwise opens behind other windows) and records `dialog.LAST_ERROR` when osascript fails for any reason other than Cancel (-128). `serve.py` then opens the remembered folder instead of starting empty, and `/api/pick` passes the error and `last_root` to the viewer; a plain Cancel still starts empty.
- The server remembers the last data root in `~/.config/dataanalyzer/last_root`; the tests point `XDG_CONFIG_HOME` at a temp dir so they never overwrite it. A long-forgotten `serve.py` on another port keeps serving old code and (on macOS) even a deleted recording; check `lsof -i :8000` when the viewer and the analysis disagree.
- The Events tab fetches one event view at a time (`fetchEvent`: `S.ev.busy` / `S.ev.pending`): while a request is out, further steps only mark that another fetch is wanted, and the then-current selection is fetched when it returns. Firing one request per arrow-key repeat and discarding all answers but the last froze the panels for seconds with detectors whose feature traces are expensive (`swr_laminar`, ~120 ms per event from 32 channels). Keep any new per-event panel on the same pattern.
- One server holds **one open recording**, shared by every browser tab and client (`DataServer.ts`, `.detections`, `.sections`, the cache). Several tabs on the same recording are fine (requests run on threads); opening another recording in one tab switches it for all of them. To look at two recordings at once, run a second server on another port. Background jobs keep the `ts` they started with and only touch `self.detections` when that is still the open recording.
- `dataanalyzer/__init__.py` deliberately does not re-export the `analysis` decorator, so `dataanalyzer.analysis` stays the module. Import the decorator from `dataanalyzer.analysis`.
